# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run from the repo root unless noted. The Rust toolchain is pinned to 1.90.0 by `rust-toolchain.toml`.

```
cargo tauri dev                 # run the app (or: npm run dev)
cargo tauri build               # build installers into src-tauri/target/release/bundle/
cd src-tauri && cargo test      # all Rust tests (db.rs unit tests)
cd src-tauri && cargo test sanitize_drops_orphans   # one test, by name substring
cd src-tauri && cargo test db::tests::save_and_load # one test, by module path
```

There is no JavaScript test runner and no linter configured. The frontend is plain JS in `src/` with no build step, so there is nothing to compile for it. `cargo fmt` and `cargo clippy` are available through the pinned toolchain but are not enforced anywhere.

## Architecture

This is a Tauri 2 desktop app. The UI is a static web page in `src/` that talks to Rust over IPC. The database is a single SQLite file in the OS app data folder (identifier `com.teamallocation.desktop`, see `tauri.conf.json`).

**The whole plan is the unit of persistence.** The frontend holds the entire plan in memory (`state` in `src/app.js`) and calls `save_plan` with all of it after every change. Rust replaces the database contents in one transaction (`db::save` in `src-tauri/src/db.rs` deletes and re-inserts everything). This is inherited from the original claude.ai web version. Do not switch to per-row updates without a reason, because the frontend's model assumes whole-plan writes.

**IPC surface.** Four commands are registered in `src-tauri/src/lib.rs`: `load_plan`, `save_plan`, `export_plan`, `import_plan`. The frontend calls them through `window.__TAURI__.core.invoke` (enabled by `withGlobalTauri` in `tauri.conf.json`). Export and import show native file dialogs from Rust, not from JS, so the file read and write happen in Rust. The frontend never touches the filesystem directly.

**Validation lives in two places that must agree.**
- `db::sanitize` in `src-tauri/src/db.rs` cleans every plan before it is saved or imported. It drops duplicates, orphan bookings, and bad dates, swaps reversed date ranges, clamps load to 10–100, and fixes project colors.
- `normalize()` in `src/app.js` does the same job on the way in, for data the frontend loads or imports.

If you change a rule in one, change it in the other. The Rust tests cover `sanitize`. Nothing tests `normalize`.

**Ghost bookings.** While the user drags to create a booking, `app.js` pushes a temporary allocation with `id: "__ghost"`. It is removed in `snapshot()` before saving, and `db::sanitize` also rejects that id. Keep both filters if you touch either side.

**Import accepts two formats.** Files from this app and files exported from the claude.ai artifact (camelCase `personId` and `projectId`) both load. The `imports_the_web_export_format` test pins the web format. Keep it passing when you change `Plan` or `Allocation` serde attributes.

**Schema migrations.** `db::migrate` uses `PRAGMA user_version`. Version 1 creates the tables. To change the schema, add a new `if version < 2` block and bump `SCHEMA_VERSION`. Do not edit the version 1 block, because existing user databases already ran it.

**Data files.** `seed/` is git-ignored and holds the real plan (people's names). Never commit it or copy its contents into tests or fixtures. Tests build their own sample data in code (`sample()` in `db.rs`).

## Gotchas

- Changing `identifier` in `tauri.conf.json` moves the app to a new empty data folder. Users must export first.
- The window permissions in `src-tauri/capabilities/default.json` grant only `core:default`. The dialog plugin is called from Rust, so it doesn't need a frontend permission. Add one only if you call the plugin from JS.
- `src-tauri/gen/` is generated by the Tauri build and is git-ignored. Don't edit it by hand.
